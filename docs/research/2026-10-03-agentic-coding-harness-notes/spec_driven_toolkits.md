## Q1. What stages and artifacts does each toolkit define, which gates need human approval, and what templates/prompts do they use?

### Takeaway
Nearly every toolkit uses the same backbone: (optional constitution/steering/standards) → requirements/spec → technical design/plan → task checklist → implement → review/verify. Each stage writes a markdown file to the repo, and a human approves it before the next slash command runs. They differ in how many artifacts they produce (BMAD and Spec Kit produce the most, OpenSpec and Harper Reed's workflow the fewest), in whether specs outlive the change (OpenSpec deltas, Tessl spec-as-source), and in how much of the implement/review loop runs without a human (see Q3).

**OpenSpec (Fission-AI)**
- 71k stars as of Oct 2026 (~52k in July 2026). Each change gets a folder `openspec/changes/[name]/` containing `proposal.md` (why and scope), `specs/` (requirements and scenarios as ADDED/MODIFIED/REMOVED deltas), `design.md`, and `tasks.md` (a checklist). Default commands are `/opsx:explore` and `/opsx:propose`. It supports 30+ assistants, is built for brownfield, and describes itself as "fluid not rigid, iterative not waterfall." — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec); [ianhxu field study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)

**obra/superpowers (Jesse Vincent)**
- The GitHub page rendered 294.7k stars (see Gaps: this figure looks anomalous). Seven stages: brainstorming (refines the idea through questions and presents the design in sections for validation) → git worktree setup (with a clean test baseline) → writing-plans ("bite-sized tasks (2-5 minutes each)" with exact file paths and code) → implementation (subagent-driven or inline) → TDD (RED-GREEN-REFACTOR) → code review (against the plan, by severity) → finishing the branch (merge/PR/discard). Humans approve the design and the plan. A `dispatching-parallel-agents` skill exists. Available for 15+ agents. — [obra/superpowers](https://github.com/obra/superpowers)
- Plans are saved to `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`. The header must include the goal, architecture, tech stack, a path to the spec, global constraints, and a "Review focus" listing failure modes no task's tests exercise. A task is "the smallest unit that carries its own test cycle and is worth a fresh reviewer's gate". Steps are atomic checkboxes (write test, run, implement, verify, commit). A self-review checks that "every spec requirement maps to a task". Execution handoff: subagent-driven (a fresh subagent per task with reviews, then a whole-branch review) or native single-session. — [superpowers writing-plans SKILL.md](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-plans/SKILL.md)

**cc-sdd (gotalab)**
- 3.7k stars, v3.0 ("major rework around Agent Skills and long-running autonomous implementation"). Requirements use EARS with acceptance criteria. Approvals are tracked in `spec.json`, and `-y` auto-approves ("humans approve the contract at phase gates"). **Anthropic feature-dev plugin (anthropics/claude-code/plugins/feature-dev)**
- `/feature-dev <description>` runs 7 phases: Discovery → Codebase Exploration (2-3 parallel `code-explorer` agents) → Clarifying Questions (waits for answers) → Architecture Design (2-3 `code-architect` agents propose minimal / clean / pragmatic options, and the user picks one) → Implementation (waits for explicit approval) → Quality Review (3 parallel `code-reviewer` agents for simplicity/DRY, bugs and conventions, and the user decides fix now or later) → Summary. Everything happens in one session. No spec files are persisted by design. — [feature-dev plugin README](https://github.com/anthropics/claude-code/tree/main/plugins/feature-dev)

**Harper Reed's LLM codegen workflow (Feb 2025; older)**
- Three steps: (1) idea honing in a conversational LLM with the prompt "Ask me one question at a time so we can develop a thorough, step-by-step spec... only one question at a time", then compile into a developer-ready `spec.md`; (2) give spec.md to a reasoning model to produce `prompt_plan.md` (a series of small code-gen prompts) and `todo.md`; (3) execute the prompts in order. A later Claude Code variant tells the agent to open prompt_plan.md, implement the next prompt not marked completed, and mark it done. — [harper.blog, "My LLM codegen workflow atm"](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/) (via snippet); [harper.blog "Basic Claude Code"](https://harper.blog/2025/05/08/basic-claude-code/)

Beck intervened in the design after earlier attempts piled up so much complexity that the AI "completely stalled". — [Beck, "Augmented Coding: Beyond the Vibes"](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes); [BPlusTree3 CLAUDE.md](https://github.com/KentBeck/BPlusTree3/blob/main/rust/docs/CLAUDE.md)

### Inferences
- The common artifact chain is: principles/steering (constitution.md, steering files, standards, project-context.md, CLAUDE.md) → requirements (spec.md / requirements.md / PRD / proposal.md / REQUIREMENTS.md) → design (plan.md / design.md / architecture.md) → tasks (tasks.md / stories / tasks.json / prompt_plan.md / PLAN.md) → implementation, with an optional review/verify step.
- The 2026 trend is consolidation and lighter ceremony. BMAD went from 14 to 8 skills and merged SM/QA into Dev. Agent OS v3 dropped spec workflows. OpenSpec and GSD position themselves as lightweight. BMAD v6.12 picks the ceremony level after investigation. Spec Kit, by contrast, keeps adding stages (assess, bug, converge).
- Human gates are almost always "the human invokes the next command after reading the file". Only cc-sdd (`spec.json` approvals), bmad-loop (configurable `gates.mode`) and Kiro's phase-approval UI record approvals as explicit state.

## Q2. How do toolkits keep the agent aligned with the spec during implementation (traceability, acceptance criteria, task checklists, drift detection)?

### Takeaway
The dominant mechanism is still a markdown checklist (tasks.md / plan.md / prompt_plan.md) that the agent ticks off, plus acceptance criteria embedded in requirements or stories. Stronger mechanisms appeared in 2025–26: Spec Kit's `/speckit-analyze` and `/speckit-converge` loop, OpenSpec's `/opsx:verify` and delta-merge archive, Kiro's property-based "Correctness" checks, superpowers' requirement-to-task mapping self-review plus fresh-context reviewers, and bmad-loop's adversarial review plus test/lint verification. Commentators still call spec drift the top unsolved problem.

### Cited Findings
- Spec Kit `/speckit-converge` gives drift detection and consistency analysis. The implement→converge loop repeats until the report says "Converged". — [spec-kit README](https://raw.githubusercontent.com/github/spec-kit/main/README.md)
- OpenSpec tasks.md is a checklist with completion tracking. `/opsx:verify` exists. Archiving merges ADDED/MODIFIED/REMOVED deltas into the main specs "keeping documentation current as code evolves". — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Kiro Correctness turns requirements into executable properties checked with property-based testing. — [Kiro docs: Correctness](https://kiro.dev/docs/specs/correctness/) (via snippet). Kiro also runs requirements analysis to find contradictions before coding. — [kirodotdev/Kiro](https://github.com/kirodotdev/Kiro)
- EARS was chosen because "its constrained natural language can be parsed by both humans and LLMs" (via snippet). — [DZone Kiro article](https://dzone.com/articles/kiro-feature-to-requirements-design-tasks)
- superpowers plan self-review: "Every spec requirement maps to a task". The plan header carries the spec path, global constraints "exact values from spec", and a "Review focus" of failure modes no tests exercise. Subagent-driven execution adds an independent review per task and a whole-branch review. — [writing-plans SKILL.md](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-plans/SKILL.md)
- cc-sdd: EARS requirements with acceptance criteria, `_Boundary:_`/`_Depends:_` task annotations, an independent per-task review when subagents are available, an auto-debug pass after failure or repeated review rejection, and learnings carried forward in "## Implementation Notes" in tasks.md. — [gotalab/cc-sdd](https://github.com/gotalab/cc-sdd)
- bmad-loop: fresh-context adversarial review sessions "avoiding anchoring bias", verification through configured test/lint commands, then commit. — [bmad-loop](https://github.com/bmad-code-org/bmad-loop)
- BMAD stories embed context and acceptance criteria so the dev agent needs nothing more (sharding). — [Augment Code BMAD guide](https://www.augmentcode.com/guides/bmad-method-ai-development) (secondary). In v6.11, `sprint-status.yaml` is the planning/execution contract. — [BMAD CHANGELOG](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/CHANGELOG.md)
- Kent Beck: plan.md is a list of tests. The agent implements only the next unmarked test and the minimal code to pass it. — [BPlusTree3 CLAUDE.md](https://github.com/KentBeck/BPlusTree3/blob/main/rust/docs/CLAUDE.md)
- Harper Reed: prompt_plan.md prompts get marked completed as they are implemented. — [harper.blog](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/) (via snippet)
- Drift is called Kiro's "#1 documented Achilles' heel", with a practitioner quote: "it just keeps drifting and drifting until you have duplication". The field study names spec drift the #1 unsolved technical problem and machine-checkable acceptance criteria the highest-ROI component (secondary synthesis). — [ianhxu field study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)
- An arXiv paper (Feb 2026, per the field study) reports that human-refined specs cut LLM code-generation errors by up to ~50%, and cautions that passing spec tests shows only that software matches the spec, not that it is correct. — [arXiv 2602.00180](https://arxiv.org/html/2602.00180v1) (via secondary)
- Böckeler observed that agents "frequently ignore the elaborate instructions anyway" (secondary quote). — [ianhxu field study quoting martinfowler.com](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)

### Inferences
- Alignment is mostly prompt-level (a checklist plus instructions) and is only enforced where a separate verifier exists: tests, property-based tests, or a fresh-context reviewer. Tools that add independent review sessions (superpowers, cc-sdd, bmad-loop, feature-dev) are moving toward verifier-in-the-loop designs.
- Only OpenSpec (delta merge) and Spec Kit (converge) have explicit mechanisms for keeping specs and code in sync after implementation. Tessl's spec-as-source would remove drift by construction but is still unproven or beta.

### Gaps
- No quantitative data found comparing drift rates across tools.
- Could not verify how Spec Kit's `/speckit-converge` works internally (diffing the spec against the code vs. an LLM judgment).

## Q3. Does any toolkit run stages autonomously/unattended with durable orchestration, or are they all human-driven slash-command sequences? Which support parallel story execution?

### Takeaway
Planning stages (brief → PRD → spec → design → tasks) are still human-gated slash-command sequences in every tool. Unattended execution of the implementation phase arrived in 2026: BMAD's `bmad-dev-auto`/`bmad-build-auto` skills and the separate `bmad-loop` orchestrator (deterministic Python, resumable state.json and journal.jsonl, worktree per story, configurable gates), cc-sdd v3's long-running `/kiro-impl`, GSD's autonomous mode with wave-based parallelism, and Kiro's Autonomous agent/Web sandboxes that deliver PRs. Durable, resumable orchestration that survives a crash shows up mainly in bmad-loop. Parallel execution is mostly limited to subagents inside one session (GSD waves, superpowers parallel agents, cc-sdd parallel markers, feature-dev parallel explorers/reviewers). bmad-loop explicitly clamps `max_parallel` to 1.

### Cited Findings
- bmad-loop: "a deterministic ralph-loop orchestrator for the BMAD-METHOD implementation phase... plain Python drives the loop — pick story → implement → adversarially review → verify → commit — while LLMs do only the creative work." State lives in `sprint-status.yaml` (or `stories.yaml`), per-run `.bmad-loop/runs/<run-id>/state.json`, `journal.jsonl` and per-task artifacts. `bmad-loop resume <run-id>`. Gates: `per-epic` (default), `per-story-spec-approval`, spec_checkpoint/done_checkpoint, deferred decisions answered later via `bmad-loop decisions`, and CRITICAL escalations that pause the run. Optional worktree isolation with a branch per story, merged locally (no auto PR). `max_parallel` is "clamped to 1 until parallel fan-out lands". Adapters for claude, codex, gemini, copilot, antigravity and opencode, with per-stage model overrides in `.bmad-loop/policy.toml`. Early open beta, v0.9.1, 146 stars. — [bmad-code-org/bmad-loop](https://github.com/bmad-code-org/bmad-loop)
- BMAD v6.10.0 added `bmad-dev-auto` ("unattended iteration driven by spec-frontmatter state machine"). `bmad-build-auto` adds review loops and deferred-work sweeps, and both "track state atomically without external event loops". — [BMAD CHANGELOG](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/CHANGELOG.md)
- Community BMAD pipelines: create→dev→review→gate loops with per-phase model switching, a feature branch per epic, PR creation, CI monitoring/fixing, and auto-merge under a GitHub auto-approve workflow (states CHECK_PENDING_PR … MERGE_PR) (via snippet). — [pi-epic-pipeline](https://pi.dev/packages/pi-epic-pipeline); [auto-bmad](https://github.com/stefanoginella/auto-bmad)
- cc-sdd v3: `/kiro-impl` is "long-running autonomous implementation". `-y` auto-approves phases. Parallel task markers allow concurrent execution on supported hosts, and execution falls back to inline when subagents are unavailable. — [gotalab/cc-sdd](https://github.com/gotalab/cc-sdd)
- Kiro: Autonomous mode builds a plan, starts a sandboxed environment, and delivers a pull request (via snippet). — [Augment Code, Kiro vs Devin](https://www.augmentcode.com/tools/kiro-vs-devin); [kiro.dev/autonomous-agent](https://kiro.dev/autonomous-agent). Kiro Web delegates multi-repository tasks in isolated cloud sandboxes, and the CLI supports headless automation. — [kirodotdev/Kiro](https://github.com/kirodotdev/Kiro)
- GSD: autonomous mode, wave-based parallel execution, and fresh subagent contexts per plan. — [gsd-build/get-shit-done](https://github.com/gsd-build/get-shit-done); [Augment Code GSD article](https://www.augmentcode.com/learn/gsd-58k-stars-claude-code)

- Task Master: interaction happens in chat via MCP, with no autopilot found in the README. — [claude-task-master](https://github.com/eyaltoledano/claude-task-master)

### Inferences
- bmad-loop is the closest prior art to a durable workflow engine driving coding-agent stages: a deterministic outer loop, an event journal, resumable runs, human gates as configurable pause states, and deferred decisions. It is still single-process, local, and serial.
- No tool found runs the whole idea→PRD→spec→plan→stories→code pipeline as a durable, distributed workflow with parallel story fan-out and human approval tasks as first-class workflow steps. That remains an open niche (relevant to Kruxia Flow).

## Q4. What critiques exist (Böckeler/Fowler, "waterfall revival", verbosity, review burden)?

### Takeaway
The main critiques: one heavyweight workflow for every problem size, large volumes of generated markdown that are tedious to review (a double review of spec then code), a false sense of control because agents ignore the specs, echoes of waterfall and model-driven development, and weak evidence of quality gains. Thoughtworks put SDD in "Assess" in Nov 2025 and, per one secondary source, dropped it as a technique in April 2026.

### Cited Findings
- Böckeler (Thoughtworks, on martinfowler.com) defines three levels: spec-first, spec-anchored (the spec is kept for evolution) and spec-as-source (humans edit only the spec). She found Spec Kit's many steps and markdown files "overkill for the size of the problem" and compared current SDD tools to "a sledgehammer to crack a nut" for small tasks (via snippet). — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); snippets via [getnima.io](https://getnima.io/blog/spec-first-vs-spec-anchored/) and [search results](https://www.rushis.com/spec-first-spec-anchored-spec-as-truth-the-three-levels-of-spec-driven-development/)
- Further Böckeler points (secondary quotes): "the tools impose the same heavyweight workflow on a bug fix and a greenfield feature". "Reviewing stacks of generated markdown is tedious and repetitive — potentially worse than reviewing code". Agents "frequently ignore the elaborate instructions anyway". Spec Kit is "really spec-first despite spec-anchored rhetoric". She invokes MDD and *Verschlimmbesserung*. — [ianhxu field study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)
- Marmelab, "Spec-Driven Development: The Waterfall Strikes Back" (Nov 12, 2025): too much text, especially in design. 1,300 lines of markdown to display a date. Double review (spec, then code). Seven failure modes: context blindness, excessive documentation, redundant three-step process, double review, agent non-compliance (skipping mandated tests), poor scaling with codebase size, and a "remove developers" ideology. 332 HN points. — [marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html) (via snippet); [ianhxu field study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md); [HN thread](https://news.ycombinator.com/item?id=45935763)
- Scott Logic (Nov 26, 2025), "Putting Spec Kit Through Its Paces: Radical Idea or Reinvented Waterfall?": the code quality was fine, but the process "burnt through a lot of agent time creating markdown files that ultimately didn't result in a better product". One test took 33 minutes and 2,577 lines of markdown to produce 689 lines of code, against 8 minutes with iterative prompting and no quality gain (via search summary; attribution of the numbers to Scott Logic is likely but unconfirmed). — [Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)
- Counterpoints: Roger Wong, "It Looks Like Waterfall (And I Feel Fine)" (Mar 2026). — [rogerwong.me](https://rogerwong.me/2026/03/spec-driven-development). Mercari's internal ASDD methodology reportedly gave a 150% speed gain over the traditional baseline and 80% over freeform-prompt AI after 6 months (secondary, original not located). — [ianhxu field study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)
- Practitioner ranking: Spec Kit scored "below both OpenSpec and BMAD", and OpenSpec scored 4.0/5 with the "lowest-friction start". — [ranthebuilder](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/) (via secondary)
- Thoughtworks Radar: SDD was placed in Assess in Vol. 33 (Nov 2025). Vol. 34 (Apr 2026) reportedly dropped it as a technique, splitting it into tool entries, and urged a "return to engineering fundamentals to combat cognitive debt" (secondary). — [Thoughtworks Radar: spec-driven development](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development)
- Kiro pricing controversy: early usage caps and opaque credit pricing. — [The Register, Jul 21, 2025](https://www.theregister.com/2025/07/21/aws_kiro_usage_cap/); [Kiro pricing blog](https://kiro.dev/blog/new-pricing-plans-and-auto/)
- The tool authors' own retreats are a critique too. Agent OS v3 dropped spec/task workflows because frontier models' plan mode "now handle much of the scaffolding". — [Agent OS CHANGELOG](https://raw.githubusercontent.com/buildermethods/agent-os/main/CHANGELOG.md). BMAD v6.12 picks ceremony "after investigation, not before". — [BMAD CHANGELOG](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/CHANGELOG.md). OpenSpec markets itself as "iterative not waterfall". — [OpenSpec](https://github.com/Fission-AI/OpenSpec)

### Inferences
- The consensus by late 2026 (secondary synthesis): spec-first is uncontroversial, spec-anchored is contested, spec-as-source is unproven. — [ianhxu field study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md). Tools are answering with scale-adaptive ceremony and verifier loops, not more documents.
- Review burden is the main practical cost, which suggests fewer, shorter artifacts and gates where humans approve decisions rather than reading whole generated documents.
