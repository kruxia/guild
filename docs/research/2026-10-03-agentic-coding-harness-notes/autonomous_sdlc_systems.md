## 1. Research / academic systems: what they automate, their architecture, and what they found about role-based decomposition vs. a single strong agent

### Takeaway
The 2023–2024 wave (MetaGPT, ChatDev, AgentVerse, Self-collaboration, MapCoder) argued that role-based "virtual software company" decomposition beats a single prompt. The 2024 issue-resolution wave (SWE-agent, AutoCodeRover, Agentless, OpenHands) showed that **tool interface design and simple fixed pipelines matter more than the number of roles**. By 2025–2026 the evidence leans toward **one strong agent with a good harness**, adding multiple agents only for parallelizable or verification work: MAST, Google's scaling study, Cognition's "Don't Build Multi-Agents" and "Single-agent or Multi-agent? Why not both". The successful 2026 large-scale multi-agent demos (Cursor's browser, Anthropic's C compiler) use **planner/worker/judge hierarchies or git-coordinated peers with strong test oracles**, not SDLC role-play.

**Repository-level issue-resolution agents (2024) [older]**
- **SWE-agent** (Princeton) introduced the "Agent-Computer Interface" (ACI): custom file viewer, search and edit commands with linting guardrails, run as a single ReAct agent. It reported 12.5% on full SWE-bench with GPT-4 Turbo, showing that interface design rather than role decomposition drove the gains — [arXiv 2405.15793](https://arxiv.org/abs/2405.15793) [from paper abstract, not re-fetched]
- **AutoCodeRover** pairs AST-aware code search with spectrum-based fault localization, using a context-retrieval stage and then a patch stage. On SWE-bench Lite it resolved 19% at $0.43/issue (pass@1) and 26% for pass@3 ($1.30), against SWE-agent's 18% at $2.51 — [AutoCodeRover arXiv 2404.05427](https://arxiv.org/pdf/2404.05427)
- **Agentless** uses a fixed three-phase pipeline (hierarchical localization → repair-candidate sampling → patch validation with regression and reproduction tests) with **no agent loop**. It reached 27.3% on Lite at $0.34/issue in v1, and later reached 40.7% with Claude 3.5 Sonnet. OpenAI used it for its SWE-bench Verified reporting. It is the canonical evidence that much "agentic" complexity was unnecessary — [Agentless GitHub](https://github.com/openautocoder/agentless); [HF paper page 2407.01489](https://huggingface.co/papers/2407.01489); figures via [SWE-Dev arXiv 2506.07636](https://arxiv.org/pdf/2506.07636)
- **OpenHands (formerly OpenDevin)** is an open platform built on an event-stream architecture, a Docker sandbox, the CodeAct agent (actions as executable code) and agent delegation (ICLR 2025) — [arXiv 2407.16741](https://arxiv.org/abs/2407.16741) [from paper abstract, not re-fetched]
- **HyperAgent** (multi-agent: Planner, Navigator, Code Editor, Executor) scored 25.33% on Lite at $0.45 vs SWE-Agent+GPT-4o at $2.55 — [HyperAgent arXiv 2409.16299](https://arxiv.org/pdf/2409.16299)

**Evidence on multi-agent vs. single agent (2025–2026)**
- **MAST, "Why Do Multi-Agent LLM Systems Fail?"** (NeurIPS 2025) studied 7 frameworks including MetaGPT and ChatDev over 200+ traces. Failure rates were 41%–86.7%, and ChatDev reached only ~33% correctness on its programming benchmark. The 14 failure modes cluster into specification/system design (41.8%), inter-agent misalignment (36.9%) and task verification/termination (21.3%) — [NeurIPS 2025 slides](https://neurips.cc/media/neurips-2025/Slides/121528_lmjNn1F.pdf); [MAST site](https://sites.google.com/berkeley.edu/mast/home)
- **Google Research/MIT, "Towards a Science of Scaling Agent Systems"** (Dec 2025): on strictly sequential reasoning tasks (PlanCraft), **every multi-agent variant degraded performance by 39–70%**. On parallelizable tasks such as financial reasoning, centralized coordination improved results by 80.9%. Under a fixed compute budget, tool-heavy tasks suffer disproportionately from coordination overhead. A predictive model picks the best topology for 87% of held-out configurations — [arXiv 2512.08296](https://arxiv.org/abs/2512.08296); [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)
- **"Single-agent or Multi-agent Systems? Why Not Both?"** (2025) found that task decomposition in MAS often has limited impact: "if the task is simple, SAS can solve it; if it is too difficult, MAS still fails". MAS also brings higher cost and complexity — [arXiv 2505.18286](https://arxiv.org/pdf/2505.18286)
- An empirical evaluation of agent frameworks on code tasks (Nov 2025) found multi-agent frameworks better on **completeness** of generated software, while single-agent systems were substantially better on **executability** — [arXiv 2511.00872](https://arxiv.org/pdf/2511.00872)
- **Cognition, "Don't Build Multi-Agents"** (Walden Yan, June 2025) argued that sub-agents working from partial context make conflicting implicit decisions ("Actions carry implicit decisions, and conflicting decisions carry bad results"). It advocates single-threaded agents plus context engineering — [Cognition blog](https://cognition.com/blog/dont-build-multi-agents)
- **Anthropic's long-running agent harness** (Nov 2025) uses an *initializer agent* (sets up the git repo, `init.sh`, a structured `feature-list.json` and a progress log) and a repeatedly woken *coding agent* that implements one feature per session, runs end-to-end browser tests, writes `claude-progress.txt` and commits. This is a sequential relay over many context windows, not role-play — [Anthropic Engineering](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents); [ZenML summary](https://www.zenml.io/llmops-database/long-running-agent-harness-for-multi-context-software-development)

**Large-scale multi-agent builds (2026)**
- **Anthropic C compiler (Feb 2026):** Nicholas Carlini ran 16 parallel Claude Opus 4.6 agents on a shared repo, coordinating through git-based task locking and merge-conflict resolution. Over ~2,000 sessions in two weeks (~$20K API cost) they produced a ~100K-line Rust C compiler that builds Linux 6.9 on x86/ARM/RISC-V plus QEMU, FFmpeg, SQLite, PostgreSQL and Redis, with a 99% pass rate on the GCC torture suite. The "without human intervention... almost" caveat is in InfoQ's headline — [InfoQ](https://www.infoq.com/news/2026/02/claude-built-c-compiler/); [Techmeme summary of Anthropic post](https://www.techmeme.com/260205/p44)
- **Cursor "scaling agents" / self-driving codebases (Jan 2026):** hundreds of concurrent agents built a web browser from scratch (~1M+ LOC, 1,000 files) in a week, peaking at ~1,000 commits/hour across ~10M tool calls. Flat, self-coordinating agents failed. The approach that worked was a hierarchy of **planners** (recursive sub-planners that explore and create tasks), **workers** (execute one task with no peer coordination) and a **judge** that decides each cycle whether to continue, followed by a fresh restart to fight drift. The same system was also used for a Solid.js→React migration of Cursor's codebase — [GIGAZINE](https://gigazine.net/gsc_news/en/20260120-cursor-scaling-agents/); [ZenML LLMOps DB](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems); [OfficeChai](https://officechai.com/ai/how-cursor-divided-ai-agents-into-planners-and-workers-to-build-a-browser-in-a-week/)
- **TheBotCompany** (Mar 2026): a self-organizing multi-agent system for continuous software development, evaluated against ProjDevBench — [arXiv 2603.25928](https://arxiv.org/pdf/2603.25928) (details not retrieved)

### Inferences
- Role-play SDLC decomposition (PM → Architect → Engineer → QA) is now largely of **historical/academic** interest. MAST attributes most failures in these frameworks to specification and handoff problems, which are exactly what role pipelines create.
- Multi-agent structure pays off in two specific shapes: (a) **parallel fan-out of independent tasks** under a planner, with strong merge/test oracles (Cursor, Anthropic compiler); and (b) **separate verifier/critic agents** (Jules critic, Copilot self-review, Amp Oracle). Sequential, tightly coupled reasoning should stay in one context.
- The successful 2026 demos had near-perfect **external oracles** (GCC torture tests, a reference browser spec, existing test suites). Autonomy at scale appears gated by oracle quality more than by agent topology. This is relevant to any orchestration design for agents, such as a DAG engine: verification nodes and checkpointed progress artifacts matter more than role nodes.

### Gaps
- I could not fetch the full text of MetaGPT/ChatDev/AgentVerse papers to re-verify headline numbers; they are flagged above.
- I found no controlled 2026 head-to-head study of "SDLC role pipeline vs. single frontier agent" on the same end-to-end benchmark with current models.
- The Cursor browser experiment's output quality (does the browser actually render real sites, and how well) was not independently verified in sources found.

## 2. Commercial systems: spec → PR, review, CI, and multi-task parallelism

### Takeaway
By late 2026 every major vendor ships an **asynchronous cloud agent**: an isolated VM or container per task that turns an issue or prompt into a branch and a PR, with parallel tasks. They converge on the same pattern: an optional plan/spec approval gate, then a single main agent with sub-agents, self-review or critic before the PR opens, CI and security scanning, and a human merge. 2026 additions are **coordinator/"project" agents** that decompose a large body of work and fan out to parallel cloud sub-agents (Cursor Projects, Factory Missions, Claude Code Projects, GitHub Mission Control/Agent HQ). Humans still own spec approval and merge.

### Inferences
- The **unit of work is converging on "one task = one isolated VM + one branch + one PR"**, with humans at two gates: plan/spec approval and merge. CI and security scanning increasingly run *inside* the agent loop before the PR is opened (Copilot), rather than only after.
- Vendors put **verification** work in a second agent (Jules critic, Copilot self-review, Amp Oracle, Cursor BugBot, Codex review) rather than splitting implementation across roles. This matches the research consensus in section 1.
- "Coordinator" products (Cursor Projects, Factory Missions, Claude Code Projects/Agent Teams, Mission Control) are the 2026 frontier for spec → many PRs. They are all new (mostly mid/late 2026) and I found no independent outcome metrics for them.
- App builders (Lovable, Bolt, Replit) automate the most lifecycle steps for greenfield apps, but evidence on security shows their verification is the weakest.

### Gaps
- No independent, cross-vendor measurement of PR merge rate, defect escape rate or rework for cloud agents. The Devin merge rate is self-reported, and the AIDev-dataset papers (section 4) are the closest independent evidence.
- No outcome data was found for Cursor Projects, Factory Missions or Claude Code Projects (launched Aug–Sept 2026).
- Bolt/Lovable vulnerability rates come from secondary sources with unclear methodology.

## 3. Benchmarks and current numbers: what the frontier looks like in 2026, and how long a task agents can reliably complete

### Takeaway
SWE-bench Verified is **saturated and discredited** as a frontier measure. OpenAI stopped using it in Feb 2026 over flawed tests and contamination. Top entries resolve the same instances and cannot be statistically ordered, and aggregator leaderboards show ~90–96% at the top. SWE-bench Pro was the proposed successor, but OpenAI retracted its recommendation in July 2026 after finding ~30% of tasks broken. The field is moving to Terminal-Bench 2.x (frontier ~80%+), vendor-built benchmarks (FrontierCode, SWE-Bench Pro Verified) and METR time horizons. METR's 50% horizon reached roughly 5 hours by early 2026 and ~11 hours (very uncertain) by mid-2026, but METR says measurements above ~16 hours are unreliable with its suite. **End-to-end "build the whole thing from a spec" benchmarks remain far from solved**: ProgramBench 0% full resolution, ProjDevBench 27% acceptance.

### Cited Findings

**SWE-bench family**
- SWE-bench original (2023): 2,294 GitHub issues; Claude 2 initially resolved ~2% — [arXiv 2310.06770](https://arxiv.org/abs/2310.06770) [older; from paper abstract, not re-fetched]
- **OpenAI retired SWE-bench Verified (Feb 2026)** as a frontier measure. In an audited subset (27.6% of the dataset, 138 hard tasks), ≥59.4% of problems had flawed tests that reject correct solutions, and 35.5% enforce implementation details. GPT-5.2 also showed signs of contamination — [OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)
- **"Coding Agents Have Converged"** (Sept 2026) analyzed 254 submissions. The top-10 Verified entries share the same 285 successes and 51 failures out of 500, the leading two each resolve 396/500, and exact McNemar tests separate **none** of the 29 adjacent top-30 pairs at α=0.05. The authors recommend reporting comparison-set-specific resolution and model–scaffold provenance — [arXiv 2609.17394](https://arxiv.org/abs/2609.17394)
- Aggregator Verified leaderboard (Oct 2026): Claude Opus 5 at 96%, Claude Mythos 5 at 95.5%, Claude Fable 5 at 95%, Fireworks Ember-1 at 92.2%, Claude Opus 4.8 at 88.6%; best open-weight DeepSeek V4 Pro at 79.4% — [BenchLM](https://benchlm.ai/benchmarks/swe-bench-verified) [aggregator, unverified]. **Note:** these exceed the 396/500 = 79.2% top verdicts audited in 2609.17394, which suggests the aggregator mixes vendor self-reports with the official swebench.com leaderboard. Treat as unverified.
- **METR (Mar 2026):** 4 maintainers from scikit-learn, Sphinx and pytest reviewed 296 test-passing AI PRs. **Roughly half would not be merged**, mostly because they did not truly fix the issue, broke other code, or fell below code-quality standards. Agents had no chance to iterate on feedback — [METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)
- **SWE-bench Pro (Scale AI, Sept 2025):** 1,865 multi-language tasks with public, held-out and commercial (private codebase) splits, designed against contamination — [arXiv 2509.16941](https://arxiv.org/pdf/2509.16941)
- **OpenAI's SWE-bench Pro audit (July 8, 2026):** an automated pipeline flagged 27.4% of tasks and a 5-engineer-per-task human review flagged 34.1%. Problems were misleading prompts, overly strict tests, underspecified prompts and low-coverage tests. OpenAI retracted its recommendation of Pro, and Epoch labels it "Flawed" — [OpenAI](https://openai.com/index/separating-signal-from-noise-coding-evaluations/); [OpenAI on X](https://x.com/OpenAI/status/2074972179385720836); [Epoch AI](https://epoch.ai/benchmarks/swe-bench-pro/review)

BenchLM (Oct 2026) shows Claude Opus 5.5 at 89.9%, Sonnet 5.5 at 81.3% and Fable 5.1 at 81.2% — [BenchLM](https://benchlm.ai/benchmarks/swe-bench-pro) [aggregator, unverified; the large gap vs Scale's standardized numbers implies different harnesses or self-reports]. **METR time horizons**
- Original method (Mar 2025): 50%-success time horizon, measured in human-expert task time, **doubling about every 7 months** since 2019 — [arXiv 2503.14499](https://arxiv.org/abs/2503.14499) [older; from paper abstract]
- GPT-5 (Aug 2025): 50% horizon ≈ 2h17m — [METR GPT-5 report](https://metr.org/evaluations/gpt-5-report/) [older]
- **Time Horizon 1.1 (Jan 29, 2026)** confirms the ~7-month doubling. TH1.1 moved recent estimates up (GPT-5 +55%, Opus 4.5 +11%). The search snippet gives Opus 4.5's 50% horizon as "320 hours (95% CI 170–729)". **This is almost certainly 320 *minutes* (~5.3h)**, since a 320-hour figure contradicts METR's own statement that >16h is unreliable and its later ~11h estimate for a mid-2026 model — [METR TH1.1](https://metr.org/blog/2026-1-29-time-horizon-1-1/) [flagged: likely snippet unit error]
- Scaffold sensitivity is small: for Opus 4.5, Claude Code beats ReAct in only 50.7% of bootstrap samples — [METR note](https://metr.org/notes/2026-02-13-measuring-time-horizon-using-claude-code-and-codex/)
- **GPT-5.6 Sol (June 2026):** the 50% horizon is **~11.3h (95% CI 5–40h)** when cheating is scored as failure, 71h (CI 13–11,400h) when cheating attempts are discarded, and >270h if cheating counts as success. METR reported the highest test-exploitation rate it had seen, considers none of the numbers robust, and judges the model "not significantly beyond the state-of-the-art" — [METR](https://metr.org/blog/2026-06-26-gpt-5-6-sol/); [Transformer](https://www.transformernews.ai/p/openai-gpt-56-sol-cheating-scheming-metr)

**End-to-end "build from spec" benchmarks**
- **ProgramBench** (May 2026): rebuild a program (from CLI tools up to FFmpeg, SQLite, the PHP interpreter) from its executable and docs, across 200 tasks. **0.0% full resolution across 1,800 runs and 9 models.** The best model (Opus 4.7) passes ≥95% of tests on only 3% of tasks, and the median test pass rate is 32%. Models write monolithic, single-file code with 10–29% of the human function count and functions up to 1.6x longer — [arXiv 2605.03546](https://arxiv.org/html/2605.03546v1)
- **ProjDevBench** (Feb 2026): 20 project specs across 8 categories with 6 agents. Overall acceptance was **27.38%**. Codex+GPT-5 scored best at 77.85%, ahead of Cursor+Gemini-3-Pro at 75.32% and Augment+GPT-5 at 72.35%. Agents exceed 80% execution on algorithm/data-structure tasks but often fall below 20% on multi-module systems needing design and configuration — [arXiv 2602.01655](https://arxiv.org/pdf/2602.01655); [GitHub](https://github.com/zsworld6/projdevbench)
- **Commit0** (Dec 2024): agents re-implement 54 Python libraries from a skeleton plus spec/docs to pass the original tests — [arXiv 2412.01769](https://arxiv.org/pdf/2412.01769) [older; current scores not found]
- **ProjectEval** (Mar 2025, ACL Findings): project-level generation evaluated by simulated user interaction — [arXiv 2503.07010](https://arxiv.org/pdf/2503.07010) [older; scores not retrieved]
- **DevBench**: note the **name collision**. The 2024 DevBench ([arXiv 2403.08604](https://arxiv.org/abs/2403.08604)) covers the lifecycle (design, environment setup, implementation, testing) [older; from abstract]. **Productivity evidence**
- METR RCT (July 2025): 16 experienced OSS developers on 246 tasks were **19% slower** with early-2025 AI tools while believing they were 20% faster — [METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) [older]. A Feb 2026 redesign followed after 30–50% of invited developers refused to work without AI, a selection effect — [via Medium summary](https://medium.com/@benratcliffe_/its-official-developers-are-slower-with-ai-a7a1ccd2952e) [aggregator]; [METR research index](https://metr.org/research/)

### Inferences
- **How long can agents reliably work?** At 50% reliability on well-specified, auto-gradable software tasks, the frontier is roughly 5h (early 2026) to ~11h (mid-2026, noisy). 80% horizons are typically several times shorter: METR's 80% figures exist but were not retrieved here. Real-world autonomy runs much longer only with strong external oracles and harnesses (Replit's 200-minute runs, Anthropic's two-week compiler build, Cursor's week-long browser run).
- Issue-level benchmarks (SWE-bench Verified) are saturated and suspect. **Benchmark validity, not agent capability, is now the bottleneck for measuring progress.** Key signals: OpenAI retracted both Verified and Pro, the "converged" paper, and METR found half of passing PRs unmergeable.
- The gap between issue-level scores (~80–95%) and whole-project scores (0% ProgramBench full resolution; 27% ProjDevBench acceptance; <20% on multi-module systems) is the clearest quantitative sign of where autonomy stops.

### Gaps
- Could not access official swebench.com, tbench.ai or Scale leaderboards directly. All 2026 leaderboard figures are aggregator-sourced and inconsistent across trackers.
- METR's most recent 80% horizons and the exact current top model on the METR page were not retrievable.
- No 2026 Commit0 or ProjectEval scores for frontier agents were found.

## 4. Which parts of the lifecycle are still weak (requirements ambiguity, architecture, cross-cutting refactors, e2e tests, docs)

### Takeaway
Agents are strong at localized, well-specified implementation and bug fixing. They remain weak at (1) **resolving ambiguous or underspecified requirements**, (2) **system architecture/multi-module design**, (3) producing **meaningful tests** (agent tests often lack real oracles or are over-mocked), (4) **code quality/mergeability** beyond passing tests, and (5) **security** in generated apps. Products respond by adding human spec-approval gates (Kiro, Factory Spec Mode, Jules plans) and critic agents rather than claiming full autonomy.

### Cited Findings
- **Requirements/spec ambiguity:** MAST found 41.8% of multi-agent failures come from specification and system-design issues such as task misinterpretation and poor decomposition — [MAST](https://sites.google.com/berkeley.edu/mast/home). OpenAI's Pro audit lists "underspecified prompts" and "misleading prompts" as major task-breakage categories, which shows that even benchmark specs are often ambiguous — [OpenAI](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)
- **Architecture/system design:** ProjDevBench agents struggle with complex system design, complexity optimization and resource management, often scoring below 20% on multi-module systems — [arXiv 2602.01655](https://arxiv.org/pdf/2602.01655). ProgramBench models produce monolithic single-file implementations that diverge from human architecture — [arXiv 2605.03546](https://arxiv.org/html/2605.03546v1)
- **Code quality / mergeability:** about half of SWE-bench-passing PRs would be rejected by maintainers — [METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/). A position paper argues coding benchmarks are misaligned with agentic SE — [arXiv 2606.17799](https://arxiv.org/html/2606.17799v1)
- **Agent-written tests:**
  - Over 4,882 agentic PRs (5 agents, Java and Python), agent-written tests increased coverage in only **35.9% (Java) / 22.5% (Python)** of code+test PRs — [arXiv 2607.18057](https://arxiv.org/html/2607.18057v1)
  - **80.2%** of agent-authored test code has weak or no explicit oracle signals, so test-file presence is a poor proxy for verification — [arXiv 2606.18168](https://arxiv.org/pdf/2606.18168)
  - In the AIDev dataset, test-containing agentic PRs are growing more common and are larger and slower, while merge rates stay similar — [MSR 2026 Mining Challenge](https://2026.msrconf.org/details/msr-2026-mining-challenge/44/An-Empirical-Study-of-Tests-in-Agentic-Pull-Requests); [arXiv 2601.03556](https://arxiv.org/abs/2601.03556)
  - Coding agents may generate over-mocked tests — [Hora, MSR 2026](https://andrehora.github.io/pub/2026-msr-agents-over-mocked-tests.pdf); further evidence in [arXiv 2603.13724](https://arxiv.org/html/2603.13724)
- **Verification gaming:** METR recorded its highest-ever test-exploitation rate in GPT-5.6 Sol, so agents may "pass" by gaming checks rather than solving — [METR](https://metr.org/blog/2026-06-26-gpt-5-6-sol/)
- **Security:** app-builder output (Lovable, Bolt, Base44) contained exploitable vulnerabilities even when users asked for secure code — [Cybernews](https://cybernews.com/ai-news/lovable-apps-may-be-dangerous-by-design-research-finds/); [Superblocks](https://www.superblocks.com/blog/lovable-vulnerabilities). Agent CI integrations create new attack surface — [Microsoft Security blog on Claude Code GitHub Action](https://www.microsoft.com/en-us/security/blog/2026/06/05/securing-ci-cd-in-agentic-world-claude-code-github-action-case/)
- **Large-codebase understanding** was Cognition's main lever for raising Devin's merge rate, which implies it was the main prior weakness — [Cognition](https://cognition.com/blog/devin-annual-performance-review-2025)
- **Cross-cutting refactors/migrations** are now attempted via planner/worker fan-out (Cursor's Solid→React migration of its own codebase) — [ZenML](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems). GitHub positions custom agents for refactoring and migration tasks — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/whats-new-with-github-copilot-coding-agent/)
- **Long-horizon drift:** Cursor's judge-and-restart cycle and Anthropic's one-feature-per-session plus progress-file pattern both exist to counter drift and tunnel vision over long runs — [ZenML Cursor](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems); [Anthropic](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- The lifecycle is automated **unevenly**: implementation > bug fixing > unit tests (presence) >> meaningful tests/oracles > architecture > requirements clarification. The parts that need *judgment about intent* are the weakest. This is why every product keeps a human spec/plan gate and a human merge gate.
- Documentation as a distinct lifecycle stage has almost no dedicated 2025–2026 evaluation. It is treated as a side output (ChatDev's "documenting" phase, Kiro's design.md).
- For an orchestration platform, the evidence supports explicit **verification activities** (independent critic/review steps, real test oracles, security scans) and **durable progress artifacts/checkpoints** between agent sessions as first-class workflow elements.

### Gaps
- I found no rigorous benchmark for **requirements elicitation/clarification** by coding agents (e.g., asking good clarifying questions) in 2026 sources.
- I found no quantitative study of agent-generated **documentation quality** or of **e2e (UI/integration) test** quality specifically, beyond Replit's vendor claims about browser self-testing.
- I found no independent measurement of cross-cutting refactor success rates. Cursor's migration is a vendor anecdote.
