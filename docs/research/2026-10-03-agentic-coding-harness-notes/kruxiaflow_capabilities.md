# Kruxia Flow capabilities and gaps as the orchestration layer for an agentic software-development harness

Scope: codebase research on [kruxia/kruxiaflow](https://github.com/kruxia/kruxiaflow/tree/a934e4c) at commit `a934e4c` ("quickstart cleanup"; last release v0.8.3). All sources are repo-relative file paths with line numbers. File paths are relative to the root of that repository. "Verified in code" means I read the implementation. I did not compile or run anything, so runtime behavior is inferred from the source. The Python SDK lives in a separate repo (`kruxia/kruxiaflow-python`), which this session could not access (GitHub MCP access was denied), so Python-worker claims rest only on in-repo docs.

Target use case: a harness that runs Claude Code agent jobs through the stages brief → spec → architecture → plan → stories → implementation/test/docs, with human review checkpoints between stages. Some of those jobs run 30 minutes to hours, there may be N parallel story implementations, and reviews may take days.

## 1. Workflow definition language: structure, dependencies, branching, loops, templating, sub-workflows

### Takeaway
A workflow is a flat YAML/JSON list of activities forming a directed graph through `depends_on`/`dependency_of`. It supports conditional edges, bounded back-edge loops (no nesting), Jinja (minijinja) templating of prior outputs, delays and absolute schedules. It has **no sub-workflows/child workflows, no dynamic fan-out (map over a list), and no nested or parallel loops**. That covers a fixed stage pipeline well, but it cannot express "for each story produced by the planner, run an implementation job" without code outside the engine.

### Cited Findings
- Top-level definition has only `name`, `activities` (a list), and optional `settings` (timeout, max_retries, budget). — [core/src/workflow/definition.rs:9-19](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs), [core/src/workflow/definition.rs:757-769](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)
- Activity fields: `key`, `worker` (default `"std"`), `activity_name`, `parameters` (arbitrary JSON, template-aware), `outputs` (output definitions), `depends_on`, `dependency_of`, `settings`, `iteration_scoped`, `iteration_limit`, `streaming`. `is_loop_activity` is computed and cannot be set by the user. — [core/src/workflow/definition.rs:632-683](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)
- A dependency edge is either a bare key string or `{activity_key, conditions|condition}`. `is_back_edge` is computed during validation. — [core/src/workflow/definition.rs:687-755](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)
- `dependency_of` is normalized into `depends_on` on the target activities after validation, then cleared (3-pass normalize). — [core/src/workflow/definition.rs:570-626](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs); described in [docs/architecture.md:1431-1448](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md)
- Activity settings: `timeout_seconds`, `retry` (max_attempts/strategy/base_seconds/factor/max_seconds), `budget` (limit + action), `cache`, `cache_ttl`, `iteration_limit`, `delay` (relative, e.g. "30m", "7d", "2mo", template-aware), `scheduled_for` (ISO 8601, template-aware), `wait_for_signal`, `streaming`. — [core/src/workflow/definition.rs:771-816](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs), [core/src/workflow/definition.rs:872-894](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)
- Conditional semantics: multiple `depends_on` edges are OR'd (the activity runs if any edge is "applicable"), and multiple conditions on one edge are AND'd. A false condition marks an edge "not applicable" rather than blocking. Mixing an unconditional sibling edge with a conditional one silently defeats the condition. — [docs/conditional-branching.md:15-31](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/conditional-branching.md), [docs/conditional-branching.md:54-95](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/conditional-branching.md), [docs/conditional-branching.md:121-128](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/conditional-branching.md)
- When an activity fails, its unconditional dependents are skipped in a cascade. — [docs/architecture.md:1720-1737](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md)
- Loops are back-edges detected at registration. Three patterns exist: fixed `iteration_limit`, conditional back-edge (default cap 100), and bounded conditional (recommended). `iteration_scoped: true` stores per-iteration outputs as arrays (e.g. `{{evaluate_results.sufficient | last}}`). — [docs/loops-guide.md:23-155](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/loops-guide.md)
- Nested loops, dynamic loop targets and parallel iterations are explicitly "Future Enhancements (Post-MVP)". — [docs/loops-guide.md:774-783](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/loops-guide.md)
- Templating is minijinja with these contexts: `INPUT`, each prior activity's outputs as a top-level key (`{{activity_key.output_name}}`, plus `.status`), `SECRET`, `WORKFLOW` (only `id` and `status`), `FILE`, `FOLDER`, `ACTIVITY` (iteration, accumulated_cost_usd, remaining_budget_usd, status), and `SIGNAL`. There is a custom `coalesce` filter. — [core/src/workflow/template.rs:144-336](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/template.rs), [core/src/workflow/template.rs:338-350](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/template.rs), [core/src/orchestrator/orchestrator.rs:447-455](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs)
- Output types are `value` (JSON), `file` (file reference) and `folder` (post-MVP). — [core/src/workflow/outputs.rs:3-16](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/outputs.rs)
- Workflow-level `settings.timeout` and `settings.max_retries` are parsed and stored, but nothing in core/api/kruxiaflow reads them. Only `settings.budget` is used. — `WorkflowSettings` usages are limited to definition, repository and DTO conversion ([core/src/workflow/definition.rs:757-769](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs), [api/src/dto/workflow.rs:51-85](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/dto/workflow.rs)); CHANGELOG notes that workflow budget was "previously parsed and silently dropped" and is now enforced ([CHANGELOG.md](CHANGELOG.md), 0.8.0 "Workflow-level budgets enforced")
- `ActivitySettings` has no `deny_unknown_fields`, so a misspelled settings key is silently ignored (e.g. `timeout:` instead of `timeout_seconds:`). — [core/src/workflow/definition.rs:771-816](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs) (no serde deny attribute; only `alias` usage is at line 716)
- Sub-workflows are absent: a grep for `sub_workflow|subworkflow|child_workflow|foreach|map_over` across docs, core, api, examples and the MCP code returns nothing relevant. The only fan-out example hard-codes `fetch_doc1/2/3` → `process_doc1/2/3` → `aggregate_results`. — [examples/03-document-processing.yaml:14-116](https://github.com/kruxia/kruxiaflow/blob/a934e4c/examples/03-document-processing.yaml)
- Definitions are versioned by timestamp. Submit takes an optional `version`, defaults to the latest, and takes an optional `unique_key` for idempotency (409 on duplicate). — [api/src/handlers/workflows.rs:24-46](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/workflows.rs)

### Inferences
- A fixed stage pipeline (brief → spec → arch → plan) maps cleanly onto a linear DAG with conditional edges keyed on review outcomes.
- Per-story fan-out needs one of three workarounds: (a) a "planner" activity that calls the REST API to submit one child workflow per story and then polls or waits for a signal (an external, hand-rolled parent/child pattern); (b) generate a new workflow definition per run, with N static story branches, and deploy it before submitting (definitions are just YAML, and MCP/REST can deploy them); or (c) fan out inside a single custom activity. Option (b) fits the engine best today, but it loses a reusable, stable definition.
- Because `{{activity.output}}` templating renders into strings and JSON parameters, passing large spec documents between stages works through JSONB outputs or files (see section 5).

### Gaps
- I did not verify whether a whole-value template (e.g. `"{{plan.stories}}"`) keeps a JSON array type or stringifies it. Code exists in `resolve_template_value`, but I did not trace it.
- The external `kruxiaflow-python` workflow-builder DSL could not be inspected.

## 2. Durability: event sourcing, retries, timeouts, heartbeats, dead letters, cancellation, crash resume, long-running activities

### Takeaway
The core is solid. It is event-sourced on PostgreSQL with a materialized state, a polling EventSource with replay-idempotent processing, a single retry authority with backoff, lease-based stale-activity reclaim, heartbeats, and dead letters that carry error messages. Activities can run for hours if `timeout_seconds` is set high and the worker heartbeats. Two serious limits stand out for this use case. First, a **global workflow timeout (default 300 s, measured from `created_at`) fails every running workflow, including one waiting on a review**, and it is not per-definition. Second, there is **no cancel/terminate/pause API**.

### Cited Findings
- Event types: WorkflowCreated, WorkflowUpdated, ActivityScheduled, ActivityWaiting, ActivitySignaled, ActivityCompleted, ActivityFailed, WorkflowCompleted, WorkflowFailed. There is no cancellation event. — [core/src/events/models.rs:67-77](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/events/models.rs)
- Every transition is an event row in `workflow_events`. Materialized state lives in `workflows.state_data` JSONB, and the orchestrator loads, applies, evaluates and saves it. — [docs/architecture.md:803-846](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md)
- The polling EventSource is used instead of LISTEN/NOTIFY because of delivery guarantees. — [CLAUDE.md](CLAUDE.md) "Service Interface Pattern"
- v0.8.1 fixed silent event drops under load: a 500 ms visibility-grace cursor, replay idempotency for WorkflowCreated/ActivityCompleted/ActivityWaiting, and a contiguous-prefix cursor advance. — [CHANGELOG.md](CHANGELOG.md) section [0.8.1]
- Retry policy: `retry.max_attempts` means total attempts (default 1, i.e. no retries). Backoff is exponential (base 2 s, factor 2, cap 300 s) or fixed. The queue owns retry-vs-terminal decisions and requeues with `scheduled_for = NOW() + backoff`. — [core/src/workflow/definition.rs:872-946](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs); [CHANGELOG.md](CHANGELOG.md) 0.8.0 "Worker-activity retry backoff", "Single retry authority", "max_attempts off-by-one"
- The queue lease works like this: `claim_next` uses `FOR UPDATE SKIP LOCKED`. A running row whose `NOW() > claimed_at + timeout_duration` (with retries left) can be re-claimed. `timeout_duration` comes from `settings.timeout_seconds`, or else the queue default. — [core/src/queue/postgres_queue.rs:120-170](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs), [core/src/queue/postgres_queue.rs:20-25](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs)
- The queue default timeout is 60 s (`KRUXIAFLOW_QUEUE_DEFAULT_TIMEOUT`). — [core/src/queue/config.rs:18](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/config.rs), [core/src/queue/config.rs:32](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/config.rs)
- A heartbeat resets `claimed_at = NOW()` (only for the claiming worker, and only while the row is running). If the activity has been reassigned, the heartbeat returns `ActivityReclaimed`, which surfaces to the worker as a 409. — [core/src/queue/postgres_queue.rs:338-400](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs); endpoint `POST /api/v1/activities/{id}/heartbeat` at [api/src/handlers/workers.rs:1129-1190](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/workers.rs)
- The orchestrator's background loop reclaims stale running activities: pending if retries remain, otherwise failed with an emitted ActivityFailed. — [core/src/queue/postgres_queue.rs:602-700](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs), [core/src/orchestrator/orchestrator.rs:2680-2750](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs)
- Rust SDK: the local execution deadline equals `timeout_seconds` (default 300 s, `KRUXIAFLOW_WORKER_ACTIVITY_TIMEOUT`), enforced with `tokio::time::timeout`. Auto-heartbeat runs every 30 s (`KRUXIAFLOW_WORKER_HEARTBEAT_INTERVAL`) only when the timeout exceeds 60 s. A 409 on heartbeat aborts the handler task. — [worker-sdk/src/poller.rs:20-21](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/src/poller.rs), [worker-sdk/src/poller.rs:285-341](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/src/poller.rs), [worker-sdk/src/poller.rs:412-434](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/src/poller.rs), [worker-sdk/README.md](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/README.md) "Configuration" table
- **Global workflow timeout:** `check_and_timeout_stuck_workflows` fails *every* workflow with `status='running' AND created_at < NOW() - workflow_timeout`, with no exemption for waiting/signal states. The default is `Duration::from_secs(300)`, configurable only through the process-wide env `KRUXIAFLOW_ORCHESTRATOR_WORKFLOW_TIMEOUT_SECS`. — [core/src/orchestrator/orchestrator.rs:2587-2672](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs), [core/src/orchestrator/config.rs:25](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/config.rs), [core/src/orchestrator/config.rs:37](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/config.rs), [core/src/orchestrator/config.rs:57-62](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/config.rs)
- The only repo file that overrides this sets 600 s (`docker-compose.examples.yml`). The quickstart `docker-compose.yml` does not set it. — [docker-compose.examples.yml:30](docker-compose.examples.yml)
- Dead letters: a WorkflowFailed reason is persisted to `workflows.error_message`, and the list/detail APIs expose `error_message` plus each activity's `error`. Processing WorkflowFailed cancels unclaimed queue rows. — [CHANGELOG.md](CHANGELOG.md) [Unreleased] "Fixed"; [migrations/20260721000001_workflow_error_message.up.sql](https://github.com/kruxia/kruxiaflow/blob/a934e4c/migrations/20260721000001_workflow_error_message.up.sql); [api/src/handlers/workflows.rs:272-298](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/workflows.rs)

- The MCP docs say: "`cancel_workflow` is intentionally absent until the engine gains a cancel endpoint." — [docs/mcp-server.md](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/mcp-server.md) "Tools (23)"
- `WorkflowStatus::Paused` exists in the enum and DB type, but nothing ever sets it. — [core/src/events/models.rs:99-105](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/events/models.rs); only read at [core/src/scheduler/mod.rs:679](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/scheduler/mod.rs)

- Doc drift: architecture.md shows `settings.timeout: {timeout, enable_heartbeat, heartbeat_interval}` for long-running activities, but the actual field is `settings.timeout_seconds` and heartbeat is automatic in the SDK. — [docs/architecture.md:1739-1753](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md) vs [core/src/workflow/definition.rs:775-776](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)

### Inferences
- **A multi-hour Claude Code activity is feasible today.** Set `settings.timeout_seconds: 14400` (for example) and run it on the Rust SDK, which heartbeats every 30 s. The server lease is renewed and the local deadline is 4 h.
- **Crash detection is slow for long activities.** No separate `heartbeat_timeout` exists: the server reclaims only after `claimed_at + timeout_duration`, and `timeout_duration` is the same value as the execution timeout. If a worker dies mid-job with `timeout_seconds: 14400`, the work is not retried until up to 4 h after the last heartbeat. Temporal-style separate StartToClose and Heartbeat timeouts would fix this.
- **Days-long review waits are impossible with the defaults.** The global 300 s workflow timeout counts from creation, so it kills a workflow waiting on human review after 5 minutes. The only workaround is to set `KRUXIAFLOW_ORCHESTRATOR_WORKFLOW_TIMEOUT_SECS` to e.g. 30 days process-wide. That also neuters the "stuck workflow / no worker running" diagnostic for every other workflow.
- When the SDK aborts a handler after a timeout or 409, any `tokio::process::Child` (e.g. `claude -p`) keeps running unless the activity code sets `kill_on_drop(true)` or kills the process group itself. This is a general tokio behavior; neither the SDK nor the std worker contains `kill_on_drop` (grep found none).
- Without cancel, a harness cannot stop a runaway or abandoned run (e.g. a reviewer rejects the whole brief) except through direct SQL or by waiting for the timeout.

### Gaps
- I did not trace whether a parallel branch failure fails the workflow immediately or only after the other branches finish.
- No crash-recovery tests were run.

## 3. Human-in-the-loop: signals, approvals, timers

### Takeaway
A real primitive exists. `settings.wait_for_signal` parks an activity in `waiting` (a durable subscription row with a timeout and an `on_timeout` of continue/skip/fail) until `POST /workflows/{id}/signal` or the MCP `send_workflow_signal` tool delivers JSON data. Timers (`delay`, `scheduled_for`) also exist. For a review-gate harness the implementation has sharp edges, though:
- the global workflow timeout kills long waits;
- a wait **cannot recur inside a loop**, which breaks the "revise → re-review" cycle;
- the `{{SIGNAL}}` template context is never populated;
- built-in std activities discard signal data;
- signaler identity is not recorded;
- README and MCP examples use field names the parser rejects.

### Cited Findings
- `WaitForSignalSettings { event_name: String, timeout_seconds: u64, on_timeout: continue|skip|fail (default fail) }`. Both `event_name` and `timeout_seconds` are required, with no serde defaults or aliases. — [core/src/workflow/definition.rs:818-845](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs); the API DTO mirrors it at [api/src/dto/workflow.rs:361-386](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/dto/workflow.rs)
- Orchestrator behavior: when a ready activity has `wait_for_signal`, it creates a subscription instead of enqueueing, marks the activity `Waiting`, and publishes `ActivityWaiting {event_name, timeout_seconds, on_timeout}`. If subscription creation fails, the activity is marked Failed. — [core/src/orchestrator/orchestrator.rs:1520-1586](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs)
- Signal semantics are "wait-then-run": after the signal, the activity returns to NotScheduled with `signal_data` stored, and is then scheduled to its worker with `signal_data` copied into `activity_queue.signal_data`. — [core/src/orchestrator/workflow_state.rs:503-529](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/workflow_state.rs), [core/src/orchestrator/orchestrator.rs:1588-1612](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs), [core/src/queue/postgres_queue.rs:76-99](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs)
- Subscription table: `activity_event_subscriptions(workflow_id, activity_key, event_name, on_timeout, timeout_at, signal_data, expired_at, …, UNIQUE(workflow_id, activity_key))`, with no iteration column. — [migrations/20260126000001_activity_event_subscriptions.up.sql:14-25](https://github.com/kruxia/kruxiaflow/blob/a934e4c/migrations/20260126000001_activity_event_subscriptions.up.sql)
- `create_subscription` does a plain INSERT, and a unique violation maps to `SubscriptionError::AlreadyExists`. — [core/src/subscription/postgres_subscription.rs:26-62](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/subscription/postgres_subscription.rs)
- `signal_activity` runs `UPDATE … SET signal_data=$4 WHERE workflow_id, activity_key, event_name match AND signal_data IS NULL`, so it is one-shot. — [core/src/subscription/postgres_subscription.rs:64-100](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/subscription/postgres_subscription.rs)
- `delete_subscription` is called only on the timeout path, after a timeout event is published. Signaled subscriptions are never deleted. — [core/src/orchestrator/orchestrator.rs:2875-2890](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs) (the only non-test caller)
- Timeout handling: a background loop marks subscriptions expired (with crash recovery via `expired_at`). `continue` publishes ActivitySignaled with null data, `skip` marks the activity Skipped, and `fail` publishes ActivityFailed. — [core/src/orchestrator/orchestrator.rs:2753-2890](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs)
- REST: `POST /api/v1/workflows/{workflow_id}/signal` with body `{activity_key, event_name, data}`. Both keys are required and must be non-empty. The response is `{signaled: bool, message}`, and an unmatched signal returns 200 with `signaled:false`. The handler ignores the caller's claims (`Extension(_claims)`), so the signaler's identity is not recorded. — [api/src/handlers/signals.rs:14-47](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/signals.rs), [api/src/handlers/signals.rs:455-563](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/signals.rs); documented correctly at [docs/api-reference.md:507-543](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/api-reference.md)
- **README example mismatch:** the README shows `wait_for_signal: approval` (a bare string) and a curl body `{"signal_name": "approval", "data": …}`. Neither matches the structs: `event_name`/`timeout_seconds` are required, and the REST body requires `activity_key` + `event_name`. — [README.md:193-210](https://github.com/kruxia/kruxiaflow/blob/a934e4c/README.md) vs [core/src/workflow/definition.rs:820-830](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs), [api/src/handlers/signals.rs:15-28](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/signals.rs)

### Inferences
- **A working single-pass review gate today** looks like this: activity `review_spec` with `worker: harness`, `activity_name: record_review`, `settings.wait_for_signal: {event_name: spec_review, timeout_seconds: 604800, on_timeout: fail}`. - There is no "signal-while-running" (an update/query to a running activity). Feedback can be injected only at gate boundaries.
- There is no reviewer identity or audit trail beyond whatever the client puts in `data`. RBAC is listed under "Later" in [README.md:405-410](https://github.com/kruxia/kruxiaflow/blob/a934e4c/README.md).

## 4. LLM-specific features: built-in activities, providers, cost tracking, budgets, MCP server

### Takeaway
LLM cost governance is the product's center of gravity:
- built-in `llm_prompt` (streaming) and `embedding` activities;
- four providers;
- a per-token cost catalog;
- pre-execution budget checks with model fallback;

## 5. Worker model: writing a custom `claude_code` activity, progress streaming, artifacts

### Takeaway
Custom activities are first-class. Any process can poll `/workers/poll` for its `worker:` queue, and the Rust `kruxiaflow-worker` crate provides a complete loop: typed handlers, auto-heartbeat, timeouts, panic containment, retryable/terminal errors, usage reporting and graceful drain. A `claude_code` activity that runs `claude -p` / the Agent SDK in a git worktree is straightforward to write. Gaps:
- progress streaming is ephemeral, in-memory WebSocket broadcast only;
- the Rust SDK client lacks file-upload and stream helpers;
- artifacts are Postgres large objects, capped by a 50 MB request body;
- there is no sandboxing or workspace management in the engine.

### Inferences
- Sketch of a `claude_code` activity, using the Rust SDK or a Python worker:
  - Parameters: `{repo_url, base_ref, stage, prompt, allowed_tools, model, max_turns}` (templated from prior outputs).
  - Handler steps: create a git worktree/branch named from `workflow_id`/`activity_key`; spawn `claude -p --output-format stream-json` (or the Agent SDK) with `kill_on_drop(true)` inside a sandbox (container or bubblewrap); forward progress lines to `/ws/token` for live viewing and also write them to a log file; on exit, push the branch, upload the transcript/diff as files, and return outputs `{branch, commit_sha, summary, result_json, pr_url}` plus `usage[]`.
  - Set `settings.timeout_seconds` to the job ceiling and `retry.max_attempts` low (agent runs are expensive and non-idempotent).
- Because streaming is not persisted, a review UI that opens after the fact sees no progress history. Transcripts must be stored as files or outputs.
- Workspace and sandbox lifecycle (worktree creation and cleanup, secrets, network policy) is entirely the worker's responsibility. Kruxia Flow provides no isolation.
- Files are keyed per `(workflow, activity_key, filename)` with no iteration, so loop iterations that upload the same filename may collide. This is an inference from the UNIQUE constraint; I did not check whether upload upserts.

### Gaps
- The `kruxiaflow-python` worker API (decorators, async support, streaming/file helpers) could not be inspected.
- I did not check whether the upload handler overwrites (upserts) or rejects a duplicate filename.

## 7. Concurrency: parallel fan-out/fan-in and dynamic fan-out

### Takeaway
Static parallel fan-out and fan-in work: independent activities schedule concurrently and a join activity `depends_on` all of them. Dynamic fan-out over a runtime list is **not supported**, and neither are parallel loop iterations.

### Cited Findings
- Fan-out/fan-in is documented, and an activity with several dependencies waits for all of them by default (AND for unconditional edges). — [docs/architecture.md:1472-1580](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md), [docs/architecture.md:1610-1633](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md)
- The example's fan-out is hard-coded to three documents. — [examples/03-document-processing.yaml:14-116](https://github.com/kruxia/kruxiaflow/blob/a934e4c/examples/03-document-processing.yaml)
- Parallel iterations are post-MVP. — [docs/loops-guide.md:774-783](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/loops-guide.md)
- Scheduling is idempotent via `ON CONFLICT (workflow_id, activity_key, iteration) DO NOTHING`, so each activity key has at most one execution per iteration. — [core/src/queue/postgres_queue.rs:76-85](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs)
- Throughput is bounded by worker concurrency (`KRUXIAFLOW_WORKER_MAX_ACTIVITIES`, default 16) and the number of worker processes per `worker:` queue. There is no per-workflow concurrency limit setting in `ActivitySettings`. — [worker-sdk/README.md](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/README.md); [core/src/workflow/definition.rs:771-816](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)

### Inferences
- "Implement N stories in parallel" requires one of: generating a per-run definition with N static branches, a parent activity that submits N child workflows over REST and joins them (by polling or with a signal back to a waiting activity in the parent), or a single activity that fans out internally. The parent/child pattern is the most reusable, and it composes with the existing `wait_for_signal`: each child's final activity calls `POST /workflows/{parent}/signal`. That only works if each child signals a distinct activity key in the parent, so N must still be known statically, or the join must be a single waiting activity that receives the last signal. A built-in map/child-workflow primitive is the real fix.

### Gaps
- No load characteristics for long-running activities were found. The benchmarks cover echo workflows only ([README.md:314-328](https://github.com/kruxia/kruxiaflow/blob/a934e4c/README.md)).

## 8. Gaps and recommended additions, prioritized

### Takeaway
Kruxia Flow already supplies the durable core: event sourcing, a queue with lease and heartbeat, retries, signals, cost and usage accounting, MCP control, and a solid Rust worker SDK. A Claude Code worker can run on it today. The blockers for a multi-stage, human-gated, days-long development harness are listed below.
- P0, blocking:
  1. per-workflow timeouts and a timeout exemption while waiting;
  2. re-entrant waits inside loops;
  3. delivering signal data to templates and std activities;
  4. cancel/terminate.
- P1:
  1. dynamic fan-out or child workflows;
  2. a separate heartbeat timeout;
  3. a generic pre-execution budget gate for custom activities;
  4. persisted progress logs;
  5. reviewer identity on signals;
  6. a workflow/review UI.
- Also fix the doc/example drift that would mislead an agent authoring workflows via MCP.

### Cited Findings (each gap's evidence, already cited above)
- **P0-1 Global workflow timeout of 300 s, ignoring per-definition `settings.timeout` and waiting state.** Evidence: [core/src/orchestrator/orchestrator.rs:2587-2605](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs), [core/src/orchestrator/config.rs:25](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/config.rs). Fix: read the definition's `settings.timeout` (already parsed, [core/src/workflow/definition.rs:759-760](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/definition.rs)) into a `workflows.timeout_at` column at submit time; exclude or extend workflows whose only non-terminal activities are `waiting`; or count timeout from last progress rather than `created_at`.
- **P0-2 A wait cannot recur in a loop** (`UNIQUE(workflow_id, activity_key)`, subscriptions never deleted after a signal). Evidence: [migrations/20260126000001_activity_event_subscriptions.up.sql:24](https://github.com/kruxia/kruxiaflow/blob/a934e4c/migrations/20260126000001_activity_event_subscriptions.up.sql), [core/src/subscription/postgres_subscription.rs:34-60](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/subscription/postgres_subscription.rs), [core/src/orchestrator/orchestrator.rs:2880](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs). Fix: add `iteration` to the subscription key, or delete/archive the subscription when ActivitySignaled is applied; extend the signal API with an optional iteration.
- **P0-3 Signal payload is unusable without a custom worker** (`{{SIGNAL}}` is never populated, and std `echo` drops signal data). Evidence: [core/src/workflow/template.rs:71-73](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/workflow/template.rs), [core/src/orchestrator/orchestrator.rs:411-457](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs), [worker/src/activities/echo.rs:14-18](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker/src/activities/echo.rs). Fix: set `context.signal` from activity state and re-resolve parameters after the signal; or have waiting activities default their output to the signal data (a built-in `human_review` / `await_signal` activity that needs no worker).
- **P0-4 No cancel/terminate/pause.** Evidence: [api/src/routes.rs:89-190](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/routes.rs), [docs/mcp-server.md](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/mcp-server.md), and `Paused` is never set ([core/src/events/models.rs:99-105](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/events/models.rs)). Fix: add a `WorkflowCancelled` event, `POST /workflows/{id}/cancel` that cancels pending queue rows and subscriptions (reusing the `WorkflowFailed` cleanup path from the [Unreleased] changelog), and propagate cancellation to running activities through the existing heartbeat 409 mechanism ([worker-sdk/src/poller.rs:412-434](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/src/poller.rs)); also add an MCP `cancel_workflow` tool.
- **P1-1 No dynamic fan-out (map over list) and no child workflows.** Evidence: section 7. Fix: a `for_each: "{{plan.stories}}"` activity setting that expands into N iteration-indexed queue rows (the queue already keys on `(workflow_id, activity_key, iteration)`, [core/src/queue/postgres_queue.rs:84](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs)) plus a join; or a `child_workflow` activity type that submits a definition and completes when the child completes.
- **P1-2 Heartbeat timeout equals execution timeout**, so crash detection for a 4 h job takes up to 4 h. Evidence: [core/src/queue/postgres_queue.rs:158-163](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs), [core/src/queue/postgres_queue.rs:612-618](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/queue/postgres_queue.rs). Fix: add a `heartbeat_timeout_seconds` setting and a `last_heartbeat_at` column; reclaim on `NOW() > last_heartbeat_at + heartbeat_timeout` independently of the overall deadline.
- **P1-3 The budget pre-check covers only `llm_prompt`/`embedding`.** Evidence: [core/src/orchestrator/orchestrator.rs:1859-1862](https://github.com/kruxia/kruxiaflow/blob/a934e4c/core/src/orchestrator/orchestrator.rs). Fix: a generic gate (workflow `total_cost_usd` ≥ `budget_limit_usd` ⇒ abort, or pause for an approval signal) for all activities, optionally with a declared `estimated_cost_usd` per custom activity; and a budget action `await_approval` that turns the README's "ask a human" into an engine primitive.
- **P1-4 Progress streaming is ephemeral.** Evidence: [api/src/handlers/streaming.rs:40-75](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/streaming.rs). Fix: an optional persisted activity log (append-only table or large object) with replay-from-offset on WebSocket connect; add `stream_token`/`upload_file` helpers to the Rust SDK client ([worker-sdk/src/client.rs](https://github.com/kruxia/kruxiaflow/blob/a934e4c/worker-sdk/src/client.rs)).
- **P1-5 Signals are anonymous.** Evidence: [api/src/handlers/signals.rs:480-484](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/handlers/signals.rs) (`_claims` unused). Fix: include `claims.sub` and a timestamp in the ActivitySignaled payload; add signal history on `GET /workflows/{id}`.
- **P1-6 No workflow/review UI.** Evidence: section 6. Fix: build the dashboard workflow list/detail (already on the roadmap) with a "waiting for review" queue, output/file viewers and approve/revise forms that post signals.
- **P2 Doc/example drift that misleads agents:**
  - the README `wait_for_signal: approval` and `signal_name` curl ([README.md:193-210](https://github.com/kruxia/kruxiaflow/blob/a934e4c/README.md));
  - the MCP authoring guide's `signal_name`/`timeout`/`delay_secs` ([kruxiaflow/src/mcp/tools/discovery.rs:365-385](https://github.com/kruxia/kruxiaflow/blob/a934e4c/kruxiaflow/src/mcp/tools/discovery.rs));
  - architecture.md's `settings.timeout.{enable_heartbeat…}` ([docs/architecture.md:1739-1753](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md));
  - the stale Python worker endpoints ([docs/architecture.md:443-510](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md));
  - the worker-sdk README map-style YAML;
  - README links to `docs/post-mvp.md`, `docs/mvp-requirements.md` and `docs/implementation/`, which do not exist in the repo (`ls` failed) ([README.md:330-335](https://github.com/kruxia/kruxiaflow/blob/a934e4c/README.md)).
  - Fix: correct the docs and consider `#[serde(deny_unknown_fields)]` on `ActivitySettings` so mistakes fail validation instead of being silently ignored.
- **P2 Other items:**
  - artifact backend limited to Postgres large objects with a 50 MB request cap ([api/src/routes.rs:251](https://github.com/kruxia/kruxiaflow/blob/a934e4c/api/src/routes.rs); S3 post-MVP per [docs/architecture.md:944-957](https://github.com/kruxia/kruxiaflow/blob/a934e4c/docs/architecture.md));
  - no RBAC/multi-tenancy ([README.md:405-410](https://github.com/kruxia/kruxiaflow/blob/a934e4c/README.md));
  - no sandbox or workspace primitives (worker responsibility);
  - no signal/query to a *running* activity (mid-job steering of an agent).

### Inferences
- Effort estimate (my judgment): P0-1 through P0-4 are localized changes in `core/src/orchestrator`, `core/src/subscription`, one or two migrations and `api/src/handlers`. The codebase's patterns (event types, idempotent replay, subscription service) already support them. P1-1 (dynamic fan-out or child workflows) is the largest design change, because it touches validation, the dependency evaluator, iteration state and templating.
- Compared with Temporal (general knowledge, not researched here): Temporal natively provides child workflows, dynamic fan-out in code, signals/updates/queries to running workflows, separate heartbeat timeouts, cancellation and unbounded waits. Kruxia's advantages are its single-binary-plus-Postgres footprint, YAML definitions an agent can author over MCP, and built-in LLM cost and budget accounting. For this harness, Kruxia is viable if the P0 items are fixed, or with workarounds: a large global timeout, unrolled review rounds, a custom review-recorder worker, and per-run generated definitions for story fan-out.

### Gaps
- No runtime verification was performed (no build, no test run). The loop-wait failure and the README-example parse failure are code-reading inferences.
- The Python SDK repo was inaccessible.
- I did not compare against Temporal or Inngest docs with web sources; the comparison above is unsourced general knowledge.
